## Method and scope

The published baseline is commit `c670e3039d2f7b43dbb00a2157e420e665203979`. A clean archive and a separate copy of the local work in progress were used for execution. The [initial state](evidence/initial-state.json) records the existing changes; the [source manifest](evidence/working-source-manifest.json) records SHA-256 hashes of the 271 tracked files before documentation was added. The working test copy excluded generated artifacts, environments, and an unused PowerShell scheduler script; production Python, Studio, and tested sources came from the local worktree.

The default Python suite ran in both copies. The fifteen core diagnostic cases ran against the local working copy. Published code was also inspected, and the authentication probe ran independently against both copies. Storage diagnostics used temporary databases and synthetic text; controlled retrieval candidates were used where the ranking operation itself was under investigation. Hash embeddings avoided external model downloads in the targeted diagnostics and browser fixture. No private memory corpus, real provider key, paid inference, or remote synchronization was used.

“Reproduced” below means the problematic behavior occurred. It is not a passing quality score, a prevalence estimate, or a measure of real-world retrieval accuracy. Priorities express the proposed release order: **P0** blocks a dependable shared service or risks losing policy/data state; **P1** materially impairs normal behavior or the credibility of evaluation; **P2** concerns optional features and cleanup.

R02 is a failure-injection experiment, not an assertion that every ordinary write loses data. It proves that the idempotency check does not establish write completeness. A shared service must commit authoritative data and its pending projection work together, then reconcile idempotently.

For R05, wings are currently classification filters. The case proves a filter/provenance inconsistency, not an exploit against an existing authenticated multitenant boundary. Promoting wing labels to permissions without changing the graph and evidence paths would create such a boundary incorrectly.

For R07, two-channel reciprocal-rank fusion with `k=60` has a maximum normal score of `2/61`, about 0.032787. A threshold presented as similarity in the interval 0–1 is therefore misleading. The code also does not order FTS matches by BM25 before treating their positions as ranks. R08's stale FTS text can influence candidate selection even though hydration reads the newer vector document.

The sync scripts can optionally include a SQLite SQL dump through `MNEMION_SYNC_KG`. That option does not make the standard drawer restore a consistent recovery of Chroma, SQLite state, source blobs, generated pages, deletions, and revisions. The report does not claim that every possible manual filesystem backup loses trust state.

R12 and R13 invalidate the stated comparative interpretation of those evaluators. They do not show that the underlying memory concepts are useless. The four moat cases can remain regression fixtures once named accordingly. The advertised 0.600 to 1.000 recall change would also be 40 percentage points, rather than a 40% relative improvement, even if measured correctly.

## Published authentication and local improvements

[probe_api_auth.py](probes/probe_api_auth.py) used a synthetic provider key and a configured Studio token. It only changed configuration path construction to keep both versions isolated.

| Request | Published baseline | Local work in progress |
| --- | --- | --- |
| Anonymous GET `/api/config` | 200; synthetic provider key returned | 403; key not returned |
| Authenticated GET `/api/config` | 200; synthetic provider key returned | 200; synthetic provider key returned |

The [published result](evidence/api-auth-published.json) and [working result](evidence/api-auth-working.json) establish the difference. Published middleware restricts mutating methods only; the local middleware covers API reads when the token is set. In both versions the token is optional and a settings response contains the provider key. This is a local-administration mechanism, not a team authentication design. Exposure depends on who can reach the service; no public internet deployment was tested or assumed.

Preserve the local read-protection improvement. For v4, separate credential administration from application access, authenticate requests by default, return redacted settings, and authorize every operation through the domain layer.

## Obsidian compatibility findings

The user's explicit requirement is to retain Obsidian for visualization. Existing behavior provides a useful base: flat YAML properties, wing/room/entity/trust links, a managed manifest, graph summaries, ZIP export, and compiled wiki pages under `_Mnemion/Compiled Wiki/`. Twelve specifically named Obsidian/export tests passed in each default suite.

A further [synthetic refresh probe](probes/probe_obsidian.py), with [recorded results](evidence/obsidian-observations.json), found:

| File type | Result after refresh |
| --- | --- |
| Unmanaged personal note alongside the mirror | Preserved |
| Manual annotation appended inside a managed mirror note | Replaced |
| Manual annotation appended in an exported compiled-wiki copy | Replaced |

This follows the existing owned-export design: [the mirror rewrites generated files](https://github.com/Perseusxrltd/mnemion/blob/c670e3039d2f7b43dbb00a2157e420e665203979/mnemion/obsidian.py#L693), and [the wiki exporter copies the compiled source](https://github.com/Perseusxrltd/mnemion/blob/c670e3039d2f7b43dbb00a2157e420e665203979/mnemion/wiki/obsidian_export.py). The wiki compiler preserves manual sections in its own source pages; that is different from preserving later edits in the exported Obsidian copy. The migration must back up the full vault and add explicit manual sections or conflict handling before refreshing existing user-edited exports.

The full owned mirror intentionally exposes quarantined notes for local review, as its tests document. The compiled wiki exporter excludes quarantined source evidence by default. v4 must preserve authorized review while giving ordinary team exports a defined policy, rather than accidentally inheriting one of these two behaviors.

No native Obsidian application was launched and no personal vault or global Obsidian configuration was changed. The [architecture](ARCHITECTURE.md) and [roadmap](ROADMAP.md) make native graph inspection and compatibility fixtures release gates.

## Additional code-review findings

| Area | Evidence and implication |
| --- | --- |
| Identity and isolation | Configuration and service objects are process-global. Core memory is keyed globally; graph entity names are global; author names are supplied as metadata. No tenant/principal/grant model governs these records. |
| Storage abstraction | `backends/base.py` exposes Chroma-shaped methods with broad keyword arguments. Registering a second backend does not reconcile the sidecar or define cross-store commit semantics. |
| Sidecar location | Several modules derive the graph database from the parent of the configured vector directory. Two sibling vector stores can resolve to the same sidecar. Path selection needs a complete store identity. |
| Cognitive scaling | `search_units` and `topic_tunnels` scan all cognitive units. Reconstruction expands topic results beyond its initial unit budget. There is no measured large-corpus latency result in this study. |
| Contradiction processing | Optional LLM decisions run in daemon threads without durable job state. Retrieval work occurs before background processing; a process exit can lose pending work. Self-reported model confidence is not a calibrated truth probability. |
| Integration contract | MCP implements JSON-RPC directly, hardcodes protocol `2024-11-05`, and is stdio-oriented. The observed registry has 47 tools and 17,263 UTF-8 bytes of serialized schema, not a measured token count. |
| Working context | Core blocks exist, but including them in an assistant's prompt depends on the client. A README statement that they are always loaded is stronger than the server can guarantee. |
| Capture breadth | Text, Markdown, JSON/JSONL, and CSV source handling exists. PDF, URL, OCR, HTTP MCP, and source/wiki frontend work remain listed as pending; the webhook module returns `not_implemented`. |
| Experimental claims | The predictor is a small LSTM trained briefly on recent embeddings. LeWM/grooming results need valid ablations and a consistent embedding-space contract before release claims. No GPU or model-quality experiment was run here. |
| Release engineering | Ubuntu CI covers Python 3.9/3.11/3.13, frontend and Electron compilation, and npm audit. It has no native Windows installer job. The Python coverage gate is 30%. Distinct package version numbers need a documented release compatibility mapping. |

The source/wiki modules already demonstrate a stronger pattern: resolve current source provenance when fetching, exporting, or constructing context. That pattern should become a common service requirement rather than remain specific to one subsystem.

## Dependency and release update work

All advisory results are snapshots of 9 October 2026. The [frontend report](evidence/frontend-audit.json) identifies 13 affected packages; the [Electron report](evidence/electron-audit.json) identifies 19. Both high-severity audit gates exit 1. The first Electron audit hit a registry error; the saved report is the successful retry's advisory response.

The Electron runtime itself is flagged high; a critical `tar` advisory is in the dependency graph. Frontend results include PostCSS, routing, and build-chain dependencies. Prioritize deployed runtime exposure and build/extraction workflows separately. Avoid `npm audit fix --force` across the whole project: major Tailwind/router/tooling changes can require code and packaging work. Rebuild and exercise packaged applications after dependency updates.

The [Python report](evidence/python-audit.json) inspected 102 installed packages in the locked working environment. It returned 35 advisory entries across 9 packages, with 23 distinct advisory IDs; some records are duplicated or related. Affected package names are `anyio`, `chromadb`, `fsspec`, `idna`, `oauthlib`, `pydantic-settings`, `python-multipart`, `starlette`, and `urllib3`. The report supplies fix versions where known. Chroma is pinned below 0.7 in the current project and its returned advisories did not supply fix versions; that requires investigation and compatibility testing rather than a guessed safe version.

The latest observed GitHub workflow for the baseline was [successful on 21 June](https://github.com/Perseusxrltd/mnemion/actions/runs/27889852169). That does not supersede today's failed advisory gates. The repository has issues disabled while publishing an issues URL as its bug tracker; restore a functional support path as part of release work.

## Reproducing the checks

Use isolated copies and temporary data, preserving the local work in progress. The clean baseline can be obtained from `git archive` at the audited commit; the source manifest identifies the working files tested. The fifteen-case diagnostic requires the working version's `MNEMION_HOME` support and refuses a version without that isolation feature.

From each isolated repository copy, the principal verification commands were:

```bash
uv sync --locked --group dev
.venv/bin/python -m pytest tests/ --ignore=tests/benchmarks -q --cov=mnemion --cov-report=term --cov-fail-under=30
.venv/bin/ruff check .
.venv/bin/ruff format --check .
```

Run the study scripts using that environment, with absolute paths to the scripts and the audited copy:

```bash
python /path/to/study/probes/probe_findings.py --repo /path/to/audited-working-copy --out /tmp/mnemion-core-observations.json
python /path/to/study/probes/probe_api_auth.py --repo /path/to/audited-copy --out /tmp/mnemion-auth-observations.json
python /path/to/study/probes/probe_obsidian.py --repo /path/to/audited-copy --out /tmp/mnemion-obsidian-observations.json
```

In each copied `studio/frontend` and `studio/electron` directory, installation used `npm ci --ignore-scripts`, followed by `npm run build` and `npm audit --audit-level=high --json`. Skipping installation scripts is why this verifies frontend assets and Electron TypeScript, not an installed Electron binary. Python auditing used `pip-audit --path <working-venv-site-packages> --format=json` from a separate tool environment.

The [validation summary](evidence/validation.json), pytest logs/JUnit reports, command-result records, build logs, and audit reports preserve the outcomes. No public dataset comparison, real-team workload, exhaustive adversarial analysis, packaged desktop run, or distributed crash matrix was completed. Proposed v4 guarantees and latency targets must be tested during implementation; the current results do not establish them.
