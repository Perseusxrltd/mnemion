# Mnemion 4.0.5

This patch adds immediate source-sync requests and scan diagnostics for issue 15.
Studio, agents and applications can request a scan on an existing connector
runner without opening an inbound port on that machine.

## Changes

- Add **Sync now**, pending-request status, last scan time, duration and change
  counts in Studio's Sources page. Older services retain their existing source
  view with a clear upgrade message for the new controls.
- Add three authenticated API operations and typed Python/TypeScript SDK
  controls. The agent catalog now covers **84 operations**. Requests use an
  expected generation to handle concurrent agents and uncertain responses.
- Store one durable control record per connector. A complete scan acknowledges
  only requests visible before it started. Overlapping requests and failed scans
  stay pending. A lost acknowledgement may cause another safe, idempotent scan.
- Watch runners check the small control record every five seconds by default;
  source scans still follow `poll_seconds` (300 seconds by default). Both are
  configurable, and remote triggering can be disabled. Errors back off without
  suppressing scheduled scans.
- Add UTC timestamps, elapsed time and changed/removed/unchanged/conflict counts
  to runner logs. Preserve complete-inventory deletion rules, permission checks,
  provider rate limits and per-scope ingestion leases.

These controls are provider independent: Git, folders/Obsidian, Drive, Slack and
rclone use the same runner loop. A source workflow can use the authenticated
API to request a scan; a native GitHub webhook receiver is still planned.
See [source synchronization](../service/connectors.md#scan-timing-and-immediate-requests).

## Server upgrade and rollback

This patch adds the bounded control table in
`012_connector_sync_requests.sql`. It changes neither embedding identity nor
Obsidian exports and requires no reindex. **Upgrade the service, workers/gateway
and connector runners together.** Studio updates automatically on supported
packages; it cannot migrate the memory server.

1. Keep the previous release checkout/environment and private deployment state.
   Stop ingestion, API/MCP and workers so the backup is the final accepted state.
2. Use the existing operator-only [backup/recovery commands](../service/recovery.md)
   to create and verify a database backup and current deletion/access ledger.
3. Install this release's locked dependencies in the new environment. With the
   database-owner credential, run `mnemion-service migrate`; runtime API and
   worker logins must retain their separate, restricted roles.
4. Start the matching service, gateway, workers and runners with their existing
   configuration. Check readiness, a scoped recall, connector status and a
   complete requested scan before reopening normal access.

Mnemion checks exact migration identities. Do not point an older service binary
at a database migrated by this patch. If rollback is needed before accepting new
writes, restore the verified pre-upgrade backup into a **separate database** with
the previous release's recovery tools and current deletion/access ledger, then
follow its activation and credential-revalidation procedure. Keep the upgraded
database for diagnosis. After new writes have been accepted, preserve them and
plan recovery explicitly; silently restoring the old snapshot would lose data.

Managed service backup/update/restart/rollback remains tracked in issue 11;
this release does not turn a source installation into an automatic server updater.

## Validation and remaining work

Local service checks passed **243 tests**, with two opt-in model checks skipped
and **86.03% service coverage**, before the last acknowledgement-loss case.
The final focused group passed 16 tests. All seven TypeScript SDK checks and
Studio's production build passed. A browser check exercised the complete sync
button/removal/status flow with isolated PostgreSQL and synthetic notes, plus an
older-server response and narrow layout. See [the dated evidence](../validation/2026-10-11-hotfixes.md).
Regression coverage exercises real PostgreSQL with restricted roles, competing
sync requests, requests arriving inside an active HTTP scan, failed/future
acknowledgements, Git commits and deletion propagation, typed client controls,
bounded control polling and compatibility with older services. Release artifacts
still require the full native and product gates.

Hosted-agent OAuth, managed remote setup and service supervision/updates,
additional memory reductions and retrieval evaluations remain on the
[roadmap](../ROADMAP.md). OS signing and first-install restrictions are unchanged;
see [desktop updates](../service/updates.md).
