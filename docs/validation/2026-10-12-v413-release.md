the successful repeats are not evidence that its cause has been fixed.

## Actual Windows desktop upgrade

The user's installed 4.0.12 app was normally reopened, verified with its saved
human administrator and hidden in the tray. Its ordinary startup update check
downloaded the published 4.0.13 installer. No manual **Check for updates** or
**Restart to update** action was used. A read-only observer confirmed that
automatic updates, background mode and startup at login were enabled throughout.

The actual Windows input idle counter passed 600 seconds. The old app exited
between **01:23:48 and 01:24:03 UTC**, the installed package changed to 4.0.13,
and a new app process started at **01:24:58 UTC**. Two samples verified the
replacement and relaunch by **01:25:18 UTC**. No inactivity threshold, feed,
installer or policy was changed for this test, and no GUI input was generated
during the waiting/install interval.

At **01:26:04 UTC**, native Windows UI Automation verified the remembered human
administrator without credential entry. The actual **Setup & this device**
page showed desktop 4.0.13 and connected workspace server 4.0.13. Automatic
updates, tray background mode and startup at login remained enabled. This
observation made no model calls or production-memory writes. It is distinct
from both the shared server update and the six-target CI rehearsals above.
