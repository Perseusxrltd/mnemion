# KeePass portability acceptance, 19 October 2026

Source: **4.23.0**. Scope: the remaining KDBX 4 import/export request in
[issue 32](https://github.com/Perseusxrltd/mnemion/issues/32), building on the
existing isolated encrypted vault. [The user guide](../service/keepass.md)
states supported algorithms, size/cost limits and deliberately omitted data.
Public native delivery remains the separate [release gate](../RELEASE_STATUS.md).

## Independent format evidence

Three committed, entirely synthetic fixtures were created and reopened with
**PyKeePass 4.2.0**, independently of Mnemion's codec. They cover AES-256 and
ChaCha20 outer encryption, AES-KDF/Argon2d/Argon2id, Salsa20/ChaCha20 protected
strings, password-only and password-plus-key/key-only access, and four standard
key-file encodings. Each has Unicode groups, standard fields, protected custom
properties, entry CustomData, an empty field, history, an attachment and a
recycle-bin entry. The manifest records exact current fields and file hashes.

The app's actual downloaded KDBX was then opened by PyKeePass. All **12 field
SHA-256 comparisons** matched, including the empty field; both entry UUIDs and
group paths matched. Its raw independently read KDF parameters were Argon2id,
32 MiB, three passes and one lane. The downloaded KDBX 4.1 file was 3,509 bytes,
SHA-256 `af22d391bb40bd98097aab85b05c7a9dd40a71980061888a5f1469d252199a2b`.
Random encryption material means later equivalent exports have different hashes.

PyKeePass is a separate validation tool, not a distributed runtime dependency.
The codec follows the [official KDBX format](https://keepass.info/help/kb/kdbx.html)
using the pinned Argon2 and cryptographic libraries, with authenticated blocks,
bounded decompression and entity-disabled XML parsing. This evidence is not an
independent cryptographic audit or a promise to preserve all KeePass features.

## Real app flow

A disposable non-owner PostgreSQL login and enabled test vault backed the actual
packaged web Studio; no fixture bridge replaced application requests. The normal
workspace-key login opened **Secrets → Import KeePass**. The preview showed two
entries, 11 nonempty credentials, one retained empty field and the three expected
omissions. No credential appeared before approval. Approval committed all 11
with only the creator's current-key grants, and clear masked labels appeared.

Selecting those credentials, generating a 32-character password, choosing the
test export password, confirming its independent storage and downloading used
the real export route. The independent field comparisons above used this browser
download. Reloading/reconnecting retained the 11 encrypted credentials.

The browser initially caught a Unicode-pattern syntax issue in the name-prefix
field. The final bundle escapes the hyphen for modern HTML pattern validation;
the actual browser accepts `team-vault_2` and rejects spaces. Cancel removed the
password form. Active transfer exposes pending-work markers to the app's existing
automatic-restart guard. Screenshots and private disposable
fixture evidence were retained outside Git; no real user vault was accessed.

## Release and scope

Migration 026 adds nullable encrypted context columns and transfer audit actions.
Existing vault values/grants are unchanged; the mapping is included in full
backups and erased alongside deleted values. Portable contents version 1 remains
supported; exports carrying KeePass mappings use version 2 and require 4.23+.

The 4.23 candidate was subsequently withheld for Intel Mac dependency resolution;
[4.24](../releases/4.24.0.md) carries the same KeePass implementation with the
compatible binding pin. Issue 32 is now associated with 4.24 for automatic closure
only after publication and installed-update evidence. Corporate key custody, managed rotation, original
office recovery, broader provider enrollment and the other open GitHub reports
remain separate work. Strict full-product coverage remains **17/64 (26.6%)**.
