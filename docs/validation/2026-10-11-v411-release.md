# Mnemion 4.0.11 publication

Published on 2026-10-11 at 21:18:48 UTC from commit
`0eb47cfe47faee135aee8fdfbd5f176cd21b2546`.

The [complete release run](https://github.com/Perseusxrltd/mnemion/actions/runs/38172952536)
passed all 30 jobs. All six Windows/macOS/Linux and x64/ARM64 targets completed
their installed workspace, update, restart-guard and relaunch gates. Native
Windows ARM retains its documented x64 backend.

Independent verification checked all 38 assets (3,862,453,237 bytes), their GitHub
SHA-256 digests, exact checksum inventory, Python web bundles, complete platform
feeds, service manifest and production Windows/macOS update signatures. The
checksum file digest was
`e2fd36ce9bc30f2f175b90cf918370b00a3643e1fa22da7fa296acf4dac85a33`.
Verification used the immutable release checkout. A 512 MiB verifier limit was
too small for the roughly 590 MiB Mac archive; the isolated verifier completed
with a 1 GiB cap after reusing only already hash-verified downloads.

The [public release](https://github.com/Perseusxrltd/mnemion/releases/tag/v4.0.11)
is stable and selected as latest. Both release-triggered metadata synchronization
jobs completed, without hand-editing the website's download URLs. The
[product page](https://www.perseusxr.com/mnemion) remains the user download entry.
An unauthenticated live page check confirmed the new version and all six installer
links without a website source edit or manual deployment.
This verifies project update signatures, not additional OS-vendor notarization
or enrollment; see [code signing](../CODE_SIGNING.md).

The release discloses the free-ngrok desktop connection problem subsequently
[reproduced and corrected for 4.0.12](2026-10-11-workspace-gateway.md).

The [public-release upgrade rehearsal](https://github.com/Perseusxrltd/mnemion/actions/runs/38175842125)
passed 4.0.10 → 4.0.11 on all six targets. Separately, the real Windows installation
downloaded, installed and relaunched 4.0.11 after its normal **Check for updates**
command. Installation/relaunch were automatic after actual inactivity; no
installer was launched manually, update policy was weakened, or system idle was
faked. By 21:35:00 UTC the old process had exited, the new version was running,
and automatic updates, background operation and login startup preferences were
all retained. Private profiles and the prepared recovery connection were kept.

This Windows observation includes manual update discovery, unlike the earlier
fully unattended 4.0.9 → 4.0.10 observation. At publication, a 4.0.12 released-app
connection check and a public upgrade from a released fixed Linux client to a
later patch remained required. Those follow-up checks subsequently
[passed with 4.0.12](2026-10-11-v412-release.md), including all six public upgrade
targets and the actual Windows administrator connection/reopen. The earlier
failing Linux case and the older-client workaround remain part of the record.
